# WebRTC Signaling for 1:1 Audio/Video Calls

This document explains what WebRTC signaling is, how it works in this project, and why it is essential for peer-to-peer audio/video communication.

---

## 1. What is WebRTC?
WebRTC stands for Web Real-Time Communication.

It is a browser-based technology that enables:
- live audio calls
- video calls
- screen sharing
- peer-to-peer data channels

WebRTC allows two browsers to communicate directly without sending all media through a central server.

---

## 2. What is signaling?
Signaling is the process of exchanging connection metadata between two peers before they can connect directly.

WebRTC itself does not define how signaling should happen. It only defines how the actual media session works after the connection is established.

So we need some communication channel to exchange information such as:
- session descriptions
- ICE candidates
- network addresses
- connection setup details

In this project, signaling is done through Socket.IO.

---

## 3. Why signaling is required
Before two users can talk directly, they need to know:
- how to reach each other over the internet
- which protocols to use
- which ports and IP addresses are available
- whether they can connect directly or need a relay

This information is exchanged via signaling.

Without signaling, the browsers cannot establish a peer-to-peer connection.

---

## 4. Internal flow in this app
In the chat socket file, the server listens for call events and forwards them to the target user.

### Socket server events used for calls
- `call:offer`
- `call:answer`
- `call:ice-candidate`
- `call:reject`
- `call:end`
- `call:busy`

These are the signaling messages.

### Example logic
```ts
const forwardToUser = (
    toUserId: string,
    event: string,
    payload: Record<string, unknown>
) => {
    if (!userId || !toUserId) return false;
    const receiverSocketId = getReceiverSocketId(toUserId);
    if (!receiverSocketId) return false;
    io.to(receiverSocketId).emit(event, { fromUserId: userId, ...payload });
    return true;
};
```

This function takes a target user and forwards the signaling message to that user’s active socket.

---

## 5. Step-by-step WebRTC flow
### Step 1: User A wants to call User B
User A opens a call and emits:
```ts
socket.emit("call:offer", {
  toUserId: userBId,
  offer,
  callType: "video",
  caller: {...}
});
```

### Step 2: Server forwards the offer
The server receives the call offer and sends it to User B:
```ts
forwardToUser(toUserId, "call:offer", {
  offer,
  callType,
  caller,
});
```

### Step 3: User B receives the offer
User B’s frontend receives the event and creates a `RTCPeerConnection` if not already present.

### Step 4: User B answers
User B creates an answer and emits:
```ts
socket.emit("call:answer", {
  toUserId: userAId,
  answer
});
```

### Step 5: Server forwards the answer back to User A
The server relays it using the same signaling path.

### Step 6: ICE candidates are exchanged
ICE candidates are network details generated by the browser. They are sent through:
```ts
socket.emit("call:ice-candidate", {
  toUserId: userBId,
  candidate
});
```

The server relays them to the other peer until a connection path is found.

### Step 7: Media starts flowing
Once the offer/answer and ICE exchange completes, WebRTC establishes a direct media channel and the audio/video stream starts.

---

## 6. What is actually being exchanged in signaling?
Signaling is not the audio/video itself. It is just control data.

Important signaling payloads include:
- SDP offer
- SDP answer
- ICE candidates
- call type (audio/video)
- caller metadata
- end/reject/busy events

### Example payload
```ts
{
  toUserId: "user-123",
  offer: {
    type: "offer",
    sdp: "..."
  },
  callType: "video",
  caller: {
    _id: "user-456",
    name: "John",
    profilePic: { url: "..." }
  }
}
```

This payload tells the browser how to establish the peer connection.

---

## 7. Why Socket.IO is used here
Socket.IO is used as the signaling channel because it is:
- fast
- easy for real-time event delivery
- already part of the app
- perfect for notifying one user about another user’s call attempt

It is not the media transport itself.

It only helps the peers discover each other and exchange connection details.

---

## 8. Why WebRTC is important in this app
This app supports 1:1 real-time voice/video communication. WebRTC is important because it:
- reduces server bandwidth usage for media
- enables low-latency audio/video communication
- allows direct peer-to-peer communication between users
- keeps the chat app closer to real-time messaging and calling experience

Without WebRTC, the app would need to send audio/video through a server, which is less efficient and more expensive.

---

## 9. Significance of the code in this project
The server-side signaling logic is the bridge that connects the two users.

It does not send the actual video stream; it only forwards the negotiation data.

This is the core idea:
- Signal channel: Socket.IO
- Media channel: WebRTC peer connection

That separation is the key to WebRTC architecture.

---

## 10. In simple words
WebRTC signaling is like the handshake before a call.

Before two people can talk directly, they must exchange a few details:
- who is calling
- who is receiving
- what kind of call it is
- how to connect
- where can I send my media

Socket.IO provides that handshake in this application.

Once the handshake is complete, WebRTC handles the actual live audio/video transfer directly between browsers.

---

## 11. Summary
WebRTC signaling is the control-plane communication that sets up the actual peer-to-peer media connection.

In this project:
- Socket.IO acts as the signaling channel
- the server forwards call offer, answer, and ICE information
- WebRTC uses that information to establish direct audio/video communication

This is the heart of the real-time calling feature.
